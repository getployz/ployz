# Verify the Caddy load

The model in `core/crates/ployz-verify/src/caddy_load.rs` explores every interleaving of the daemon's `watch_caddy` loop with the Ingress Proxy it drives. Each watcher step is one statement of `watch_caddy`, `apply_caddy`, `CaddyLoad` (in ployz-decide) or `CaddyCertificates::find_refused`, with every outcome the code handles: the admin found, down or failing to connect; `write_certificate_files` and `remove_stale_certificate_files` each succeeding or failing; `caddy::load` succeeding, refused, failing short of Caddy, or taking while its response is lost; `write_caddyfile` succeeding, failing before its rename, or failing after it; a load refused by the admin and the probe that follows; the projection read failing. Caddy is an actor outside the watcher: it restarts in place under the same container id, is replaced by a new container, stops and starts, and a started Caddy serves the Caddyfile on disk. The replicated store changes the projection. The model holds the real `CaddyLoad` and calls its `skip`, `after`, `refused_by` and `claim`, so a change to those rules changes the explored states. The `watch_caddy` statements around them are a hand copy, and drift unless you keep them in step.

The claim is `PublishedRoutes.addresses`: the routed addresses that `ployz status` and Deploy evidence read as what the Ingress Proxy serves. Two properties about it, judged only at rest:

- `CLAIM_SERVED`: **at rest, the published addresses are what Caddy serves.** The claim is `None`, or it names the addresses of the config Caddy's process serves. It fails on an over-claim (`Some(P1)` while Caddy serves `P0`) and on an under-claim (`Some(nothing)` while Caddy serves routes).
- `CLAIM_CONFIRMED`: **at rest, a claim of addresses names the Caddy that confirmed it.** A `Some(config)` claim comes from a `Loaded` or `Served` load, whose input names the container that confirmed it.

At rest means the watcher waits after a pass that read its inputs, in the debounce wait or in the retry sleep after a failed apply, and no Caddy event has landed since. The harm when `CLAIM_SERVED` breaks: `ployz status` and Deploy evidence show every route confirmed while Caddy serves an older config, or one with a site left out, so a Deploy reads reachable when it is not. What keeps each stale claim standing on real code, and its first chance to reconcile, is under [How long a stale claim stands](#how-long-a-stale-claim-stands).

## Run it

```
cd core && cargo test -p ployz-verify caddy_load -- --nocapture --test-threads=1
```

Under ten seconds warm; the whole crate takes about 40 s because of the Volume Runs model beside it. One test thread keeps each story in order under its test's name, which prints in brackets above it. CI runs it in the workspace nextest, so a red model blocks the PR.

The run is green when all ten tests pass. Read them as three groups:

- **The open findings.** `current_code_keeps_a_claim_after_a_load_that_lost_its_response` and `current_code_keeps_a_claim_after_a_restart_between_the_load_and_the_caddyfile_write` each pass by *finding* a counterexample on the code as it is, and print it. Each turns on one event (`loads_lost`, `restarts_mid_apply`) over the `QUIET` bounds, so the printed path needs that event and nothing else the code does not already answer for. Each is red on code that closes its path. When a product fix lands, flip the test it closes: model the fix as the code wrote it, assert the property holds, keep the old path as a `Broken` flag's test, and move it into this skill as history.
- **Where the code holds.** `current_code_holds_while_caddy_restarts_between_passes_and_reads_fail` runs the code as it is with restarts in place between passes and failed reads over `QUIET`; every load answers and no restart lands mid-apply. Caddy still stops, starts and is replaced; loads are refused and probed; writes fail before and after the rename; the projection changes. It prints a state count and checks every property and every `sometimes`. A `sometimes` that is never reached fails here: the model can no longer reach that outcome, so a property passing beside it proves nothing. Each `sometimes` is one row of the `COVERAGE` table, naming one call outcome, record or Caddy event, and its predicate reads that event from the state that recorded it: `last`, the action that led there; the record `Pc`; or the unseen Caddy event. `every_sometimes_needs_what_it_names` runs with every bound on, then takes each row's `omit` out of the model (the actions, the record, the event, or the kept record) and expects the row unreached. A row reached without its cut is vacuous, its predicate looser than its name, and that test is red until the predicate names the event. The cut proves something only where the predicate says more than the cut takes out: a row reading `last == Some(X)` with `omit: Actions([X])`, a record `Pc` with `Omit::Record` of it, or an unseen event with `Omit::Event` of it, cannot be reached without its cut, and most rows are of that shape; for them the test records that the outcome stays reachable. The cut tests the eight rows whose predicate adds a condition: the admin load that claims the projection, the before-rename failure in the `AfterServing` arm, the candidate refused with `c` quarantined, the stale-file refusal, the failed read ending at the wait, the restarted Caddy serving an older Caddyfile, the new container confirming, and the stopped Caddy claiming nothing.
- **The guards.** `the_keep_rule_needs_the_caddyfile` and `a_refused_probe_must_record_before_it_rederives` drop the two guards that closed findings 1 and 2 and print those paths. `the_cache_needs_a_running_caddy`, `a_reloaded_probe_must_clear_the_recording_caddy`, `the_keep_rule_needs_the_recording_container` and `the_record_needs_the_admins_confirmation` each drop an older guard. Each sets one `Broken` flag and expects the property to fail. One of those going green-to-red means a guard no longer earns its keep, or the model lost the path that shows it.

## Read a counterexample

A failure prints the test name, the property name, the model's flags, and a numbered story cut at the first state that breaks the property, so the last row is the broken state. Each row is one statement in the code's words, or one Caddy or store event, with the claim, Caddy and the watcher's locals once it ran, for example:

```
 7. watcher: caddy::write_caddyfile fails through the admin before the rename: Err(AfterServing), the Caddyfile still holds P0 (apply_caddy, filesystem::atomic_write)
    claim=None load=Unapplied | caddy X serves P1 file P0 | projection P1 accepted=false refused=false
```

`claim` is the claim: `None` is unconfirmed, `Some(nothing)` is the empty map a stopped Caddy gets, `Some(P1)` names the addresses of config `P1`. `load` is the watcher's `CaddyLoad` (`Unapplied`, `Written`, `Loaded` or `Served`) with the input and container it holds. `caddy X serves P1 file P0` is the ingress container, what its process serves and what the Caddyfile on disk holds; `(unseen: Restarted)` marks a Caddy event the watcher has had no pass to read. `projection` is what `next_pass` derives before `quarantine`. `last_input`, `accepted` and `refused` are the watcher's locals: `P1/X/admin` is a `CaddyInput` for projection `P1` and container `X` loaded through the admin, `file` one written without it, and the two flags are `CaddyCertificates` for the one pinned certificate `c`. `P1WithoutC` is `P1` with `c`'s material left out, which a probe loads, `loaded_only` writes while `c` is unaccepted, and `quarantine` derives once `c` is refused; without material the HTTPS site has no route, so its addresses differ from `P1`.

Write the story out in the watcher's words before deciding anything: which pass wrote the claim, through which path, and what Caddy served by then. A test that fails inside `assert_properties` prints the raw `Path[n]` of actions instead; to see the rows, call the module's `breaks` helper with that model in a scratch test, which prints the story.

If a picture would help, the pstack `/statechart` skill draws how a model moves between states and tells each shortest failing path in plain words. Refer to it by name; its commands change between releases.

## Real bug or model error

A counterexample is a **lead**, not a verdict. Confirm each step of the story against the function it names before calling it a bug. Each `Pc` and `Action` variant's doc comment names its file and function, and `reads_as` prints the statement each step copies.

- If a step does something the code cannot, fix the model and say so. The usual suspects: a Caddy event the model lets land where the code could see it (`unseen` and `at_rest` decide which states the property judges), an outcome `apply_caddy` cannot return from that call (`BeforeServing` against `AfterServing`), what a failed call left behind (a `Load::Lost` has Caddy serving the config, a `Write::FailedAfterReplacing` has the file replaced), and what `find_refused` leaves in `accepted` and `refused` on each of its exits.
- If every step matches the code, it is a finding. Report it in plain words with the path. Keep the property and the model as they are; weakening either to go green hides the bug.

The three findings this model was built on, confirmed step by step on `main` at `1e3ada53e2`, each with the path its test prints. The first two are closed (below); their paths are what the guard tests print now.

1. **The claim outlived an in-place restart (#2787).** Caddy loads `P1` through its admin, then `write_caddyfile` fails before its rename, so `apply_caddy` returns `AfterServing` and the Caddyfile still holds `P0`. The `(AfterServing, true)` arm accepts the certificates, and the record write claims `P1` with `recorded_by` the container. Caddy restarts in place under the same id and serves the Caddyfile, `P0`. The watcher never sees the restart, since the replicated observation carries no start time. The next pass fails before serving (here `write_certificate_files`; `caddy::load` failing short of Caddy reaches the same arm), and the keep rule finds `recorded_by == caddy` and leaves the claim at `P1`. The comment above the keep rule admitted this path; the model showed it needs only one failed write and one restart. The path is 18 rows. Closed: `ApplyError::AfterServing` now says whether the Caddyfile holds the load (`CaddyFile`), and `CaddyLoad::refused_by` keeps a load only while it does, so this pass claims nothing. `the_keep_rule_needs_the_caddyfile` prints the path.
2. **A refused probe skipped the record write.** Caddy `X` confirms `P1` after a write that failed before the rename, so the Caddyfile holds `P0`, and a new container `Y` replaces it and serves that file. The next pass loads `P1`; the admin refuses it, and `find_refused` runs: `loaded_certificates` shows no `c`, the load without `c` takes, so Caddy serves `P1WithoutC`, and the candidate with `c` is refused twice, so `c` is quarantined. `Probe::Refused` clears `recorded_by` and `continue`s to the top of the loop without the record write. The next read fails, and its `Err` arm only logs, so the watcher waits on the claim from the pass before, `Some(P1)`, while Caddy serves `P1WithoutC`. Any earlier claim does. The path is 22 rows. The replacement is one way for `loaded_certificates` to come back without `c`; a confirmed `P0` with the projection changed to `P1` is the other, at the same length and on container `X`. Closed: the record write runs before `Probe::Refused`'s `continue`, so the claim is written on every exit from a pass. `a_refused_probe_must_record_before_it_rederives` prints the path.
3. **A lost load keeps the old claim.** Caddy confirms `P1` and the projection changes to `P0`. `caddy::load(P0)` reaches Caddy, which applies it, and the response is lost: `AdminClient::post` sends the body and awaits the response under `ADMIN_TIMEOUT`, so a timeout or a dropped connection comes back as `caddy::Error::Http`. `apply_caddy` returns `BeforeServing`, which the code reads as Caddy unchanged, so no probe runs, `refused` is true, and the keep rule finds `recorded_by == caddy` and leaves the claim at `P1` while Caddy serves `P0`. No restart and no failed read is needed. On `1e3ada53e2` the path got its claim from a `write_caddyfile` that failed before the rename, 19 rows. The code now keeps a claim only while the Caddyfile holds it, so the path writes the file first, 20 rows, and the test asserts the over-claim with `claim_is_written`. Open.

## What the code leaves open

The code holds with restarts in place between passes and read failures on. It does not close #2787 in full:

- **A restart between `caddy::load` and `write_caddyfile`** (`restarts_mid_apply`). Caddy loads `P1` through its admin, restarts in place and serves the Caddyfile, `P0`; the write then lands `P1`, `remove_stale_certificate_files` succeeds, and the pass claims `P1` with `last_input` set. Every later pass hits the `loaded` cache (`!no_caddy && load.skip(..)`), which skips the admin while Caddy runs and the last load matches, so no retry, debounce or resnapshot pass corrects it; its first cache miss is the next projection or ingress container change, or Caddy stopping, and that pass can keep the claim too (the keep rule keeps it when the write fails before serving with the container unchanged and the Caddyfile holding what was recorded). `current_code_keeps_a_claim_after_a_restart_between_the_load_and_the_caddyfile_write` prints this path (15 rows). The bound allows one such restart per apply, only through the admin, and only while no other Caddy event is unseen.
- **A lost load** (`loads_lost`), finding 3 above. For a fix: only `admin.load` inside `caddy::load` (`caddy.rs`) leaves Caddy's state unknown on an error, since `Http` from `adapt`, and every `Io` and `Json` error, come before Caddy changes; treating `BeforeServing` as unknown must split on which call failed, not on the error type. `find_refused`'s load without the suspects maps any error to `Probe::Unchanged` (`ingress.rs`, the `is_err()` guard before the candidates), a second site of the same finding. A lost candidate load is already safe: it reads as `Probe::Reloaded`, which leaves `CaddyLoad::Unapplied`.
- **A restart in the retry sleep after a stale write** (follow-up E-20b, on `main` too). A pass whose `write_caddyfile` fails through the admin ends in `CaddyLoad::Served { file: Stale }`, and `claim` names the new load. If Caddy restarts in place during the `WATCH_RETRY` sleep that follows (1 s), it serves the older Caddyfile while the claim names the new load. `Served` never skips, so the next pass that reads its inputs and finishes reconciling reloads or withdraws the claim; a failed read keeps it. The model does not see this window: `at_rest` needs `unseen.is_none()`, and the restart stays unseen until the retry's `Read`.

Each needs its own remedy. The mid-apply restart needs the watcher to see the restart, a start time in the observation, since nothing in its locals changes. The lost load has no restart and no start time to see: it needs Caddy's config read back through the admin, or a probe, before the record write, or the uncertain claim dropped.

## How long a stale claim stands

The model judges the retry sleep and the debounce wait as at rest, so each path above counts as a break. On real code one rule holds: a stale claim ends only when a pass's record write (`route_publishes.send_if_modified` in `watch_caddy`, from `CaddyLoad::claim`) replaces or withdraws it. Nothing else touches `PublishedRoutes.addresses`. On every open path below, the next pass can fail in the same way and keep the claim, so the last column is a chance, not a recovery.

| path | what keeps it standing | first chance to reconcile |
|---|---|---|
| finding 3, the lost load | each retried load loses its response again (`BeforeServing(Http)`), and `CaddyLoad::refused_by` keeps the load, since the container is the same and the Caddyfile holds it | `wait_before_retry`, `WATCH_RETRY` (1 s), then the next pass |
| the mid-apply restart | `CaddyLoad::skip` holds on `CaddyLoad::Loaded`: the same projection and the same container, with `!no_caddy`. No retry, debounce or resnapshot pass corrects it, since each hits the cache | the next projection or ingress container change, or Caddy stopping: each misses the cache, and the pass goes through the admin or claims for a stopped Caddy |

Before the fix, finding 1 stood while each pass through the admin failed before serving (one retry per `WATCH_RETRY`), and finding 2 while each read failed (one retry per change or `WATCH_RESNAPSHOT`).

## A break that stays green

Guards overlap, so removing one can leave every property holding. Before calling a guard dead, rerun with a neighbouring `Broken` flag set too. `the_keep_rule_needs_the_recording_container` only shows the container check's worth with the Caddyfile check out (`keep_ignores_the_caddyfile`) and restarts off: with the Caddyfile check in, a new container that started from a stale file is already refused a stale claim, and with restarts on, finding 1 breaks the property first. That is why the Caddyfile check is not the whole guard: the keep rule must still name the container, or a replacement inherits the old container's claim on its first refusal.

## Keep the model in step

When a change intentionally alters the loop (a new guard, a new statement, a reordered call, a new `ApplyError` shape, a new `Probe` arm), change the model in the same PR:

1. Update the matching `Pc` variant, `Action`, or `step`'s arm, citing the file and function it copies, and the `reads_as` line that prints it.
2. If the change adds a guard, add a `Broken` flag that removes it and a `breaks` test naming the property it keeps. A guard with no failing variant is untested.
3. If the change fixes a finding, flip its test as described under Run it. Do not delete it: its printed path is the record of what the fix keeps out.
4. If a property's meaning changes, change its text and say why in the PR body. Narrow a property only when the code is right and the property was wrong about the design.
5. If the change adds an outcome, add a `COVERAGE` row naming it, with the `omit` that takes it out. `every_sometimes_needs_what_it_names` fails the row while any other path reaches its predicate.
6. Move the sync commit below forward only after you confirmed each covered function still reads as the model says.

## Bounds and blind spots

Bounds: one Machine that takes ingress, with one ingress container at a time, `X`, replaced at most once by `Y`; two projections, `P0` with one HTTP site and `P1` with that site moved and an HTTPS site pinning one certificate `c`; Caddy events (restart in place, replace, stop, start) only while the watcher waits, and one per wait, except the one mid-apply restart `restarts_mid_apply` allows; the projection changing only while the watcher waits. Each `CaddyLoad` field is a bound: `restarts`, `restarts_mid_apply`, `reads_fail` and `loads_lost` turn an event on over `QUIET`. The property judges a state only at rest: the watcher waits, and no Caddy event has landed since the pass that put it there. A window between a Caddy event and the pass that reads it is not the watcher's to close, so the model does not count it.

Out of scope: the lag of the replicated observation behind a Caddy event, since `Read(Ok)` exposes a replacement at once while `newest_local_ingress` reads an observation that can lag it; the route acks and `PublishedRoutes.routes`; `down` and the kept route; two pinned certificates; the role turned off and a Machine with no ingress container; the admin confirming a load that Caddy then drops; Caddy events during a pass other than the one mid-apply restart; the equal-input skip through the admin, which the code reaches only when the store says no Caddy while the admin socket still answers (that lag again), so the model reaches it only without the admin. A green model says nothing about them; cover them with the watcher tests in `core/crates/ployzd/src/caddy_tests/watcher.rs` (`cargo nextest run -p ployzd --lib ingress::caddy::tests::watcher`).
