# Namespace Revision Entry Identity Is A Versioned Per-Service Digest

Deploy planning decides service container reuse by comparing a namespace revision entry identity: a hex-encoded sha256 digest over a versioned canonical encoding of the fields that require container replacement: namespace id, service id, image reference, the container runtime controls that Docker applies at create time (healthcheck, restart policy, Linux capability add/drop, and resource limits), volume mounts, and an opaque keyed environment contribution. Namespace id and service id are folded into the digest so two namespaces or two services never share an identity even when their container shape is otherwise identical, which keeps the id safe to use as a standalone lookup key in labels, projections, and gateway matching. The current encodings are entry v11 and namespace v9. The encoding carries an explicit format version so a change to which fields the identity covers is a deliberate, detectable version bump instead of silent drift that would mass-replace every running container after an upgrade.

Control derives one process-memory-only environment revision key from its Controller NKey seed with an explicit HMAC-SHA256 key-derivation domain. Environment names and values are sorted by the typed environment map, encoded as length-framed name/value pairs under a separate HMAC domain, and contribute only that HMAC result to the outer revision digest. The key has redacted debug output and is neither serializable nor part of evidence, labels, logs, or wire contracts; the standalone HMAC is likewise never exposed. Preview and authoritative execution receive the same key and use the same identity path. The same Controller seed and environment therefore reuse revisions across operations, restarts, and promotion, while a changed name or value changes the revision. A different Controller seed deliberately causes conservative replacement. Empty environments contribute nothing, so their revision identities are key-independent.

The identity deliberately excludes replica count, route targets, and routed endpoint ports (ADR 0023 makes endpoint ports route state, not container state). Registry images are resolved before the final plan, so the image frame carries the digest-pinned reference. Mutable tags never enter the final namespace revision entry identity or committed namespace manifest.

For pushed images, `index_digest` is a Ployz receipt-index identity rather than the digest of a served OCI image-index blob. Its versioned canonical encoding sorts entries by OCI platform and frames each platform's OS, architecture, manifest digest, and image id. Seed machine location is excluded, so relocating identical content does not replace service containers. Core computes and validates this identity whenever a receipt is constructed or decoded; producers cannot supply an independent digest for different platform content.

The identity is an opaque digest, not a field-by-field spec comparison, because it must travel through immutable Docker labels and machine observations and be compared by components that never see the full deploy input.
