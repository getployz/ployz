# Deploy Replacement Is Explicit Policy With Failure Evidence

Ployz deploy planning should make container replacement policy explicit: services may run pre-start hooks before run or replace work, replacements use an update order such as `start-first` or `stop-first`, newly created containers with a required healthcheck must pass their one-time creation gate before the phase can continue, and failed hook or service containers are retained as failed deploy evidence. A `start-first` service update should promote healthy new containers, then stop old containers with a bounded per-service stop grace period; stop grace waits for services in the same phase may run in parallel and default to 10 seconds. A `stop-first` replacement should stop the old container with the same stop grace period before starting the replacement; if Docker force-kills the old container after the grace period and reports it stopped, Ployz records warning evidence and continues, but if the old container remains running or cannot be stopped, Ployz fails before starting the replacement. For routed service promotion, Ployz should start a role observation window at promotion and run it concurrently with old-container stopping; the window lasts at least `max(configured role observation minimum, actual old-container stop wait)` even on first deploys and even if gateways converge early, with an initial platform default of 5 seconds, and missing convergence emits warning evidence without blocking phase completion. If a `stop-first` replacement fails after stopping a previously running old container, Ployz should best-effort restart the old container and report both the replacement failure and restart outcome.

For routed service removals, cleanup should perform serving unpublish first, observe gateway role processes through the role observation window, then stop and remove runtime containers with the service stop grace period. Missing role-process convergence during removal emits warning evidence but does not fail cleanup; cleanup failure is reserved for serving unpublish state changes, Docker stop/remove, or other actual cleanup work failures.

Hooks and migrations must be safe to retry: there is no durable hook-success ledger, hidden rollback engine, or event replay path; the next deploy observes runtime state and plans again.
