# Management Capability connection candidates

SSH and the Management Capability share the existing Machine RPC Connector and identity confirmation. Cloud stores `organizationMachine` as encrypted backend-only connection metadata, scoped by Organization, Machine and current pairing; it is neither membership nor presence.

The authenticated founder publishes its candidate before completion. The enrollment claim fixes the intended Machine and pairing generation, while its Management Capability may rotate. An authenticated retry may replace the capability only after shared negotiation verifies the intended Machine; publication rechecks the current claim and unchanged saved candidate after verification, without holding a database lock across the network call. The current claim records the intended Machine as well as its public key; shared negotiation must confirm that Machine before transactional first-connect admission. Matching retries resume even after a lost completion response. Candidate absence and transport failure never authorize founder transfer or reset; reset remains unavailable until endpoint revocation can be confirmed.

The greenfield database history is a single baseline containing the current schema. It initializes fresh databases. Every new pairing must name a non-null 32-hex founding Machine ID.

Supported Machine RPC connections use local sockets, SSH, or the in-process iroh management transport: the daemon serves Machine RPC on its Management Identity, and clients dial it through the self-hosted Ployz Relay, upgrading to direct paths when they work. Set stages a fresh public client key while retaining the accepted key. Authenticating and negotiating DescribeContract with a pending key only verifies identity; it does not change the accepted key. Cloud commits the verified candidate before issuing operational RPCs. The first operational RPC activates the replacement, so removal racing verification retains a usable saved credential. Lost issuance responses leave the old key usable for retry. Only public client keys are persisted by the daemon. A CLI enrolling through a saved Management connection durably replaces its local capability before publishing it to Cloud, so activation followed by a lost HTTP response leaves the same command retryable. Pairing and key handover are one tagged persisted state; unpaired records cannot contain client keys. Each management RPC checks its key at dispatch, and local mutations recheck after acquiring admission, including queued Build work. Clear rejects queued work whose key has been revoked; work that already acquired admission may finish. Removing a pairing clears both accepted and pending client keys in one mutation and closes its connections; a successful Clear or an authenticated response confirming that both client keys and the pairing are cleared is removal confirmation. Refusal of a replaced key and an unreachable Machine stay unconfirmed.
