# X. DNS authority report

Read-only investigation for thread X, scoped by [external-authority.md](external-authority.md) section X. No runtime files, domains or services were changed. No secret values were read or printed.

## Bottom line

Hosted DNS runs **on np1**, next to Cloud. `getployz/ops` deploys `ployz-hosted-dns` from `np1/compose.prod.yaml` with `.env.hosted-dns.production` on np1, and `dns.ployz.app` resolves to np1's address. So root on np1 holds more than Cloud's per-name bearer tokens. It also holds what the service itself runs with: Route 53 credentials for the `ployz.app` zone, the ACME (Google Trust Services) account, and the Hosted DNS database. That lets np1 skip the API. It can rewrite any record in `ployz.app` and get a certificate for any name under it. That covers every Organization on hosted Cloud and every Self-hosted Cloud, which also use `https://dns.ployz.app/`.

Recommendation: **separate authority**. Narrowing the API changes nothing while np1 holds the credentials behind it. Moving the service off np1 alone is also not containment, because np1 keeps every per-name token and could still ask the moved service for the same effects. Both are needed:

1. Move Hosted DNS, its Route 53 credentials, ACME account and database to an administrative domain that np1 root cannot reach.
2. Make the service refuse address changes, retirement, token rotation and certificate requests unless they are signed by customer-held authority that the service pinned for that name. With that, TLS keys for generated domains live on Machines, not in Cloud.

Concrete rejected requests are in [Proposal](#separation-proposal).

## Recommendation

| Option | Verdict | Why |
| --- | --- | --- |
| Keep the boundary | Reject | It fails the promise for every generated domain. It also reaches past Cloud's own data: the whole `ployz.app` zone, Self-hosted Clouds, and certificate issuance from any CA. |
| Narrow the API (sign requests, bind CSR key, drop `rotate`) on np1 | Reject alone | np1 holds the Route 53 key, ACME account and DB behind the API. It skips the API. |
| Move Hosted DNS off np1 with today's API | Reject alone | np1 keeps every per-name token (`APP_ENCRYPTION_SECRET`), so it can still ask for the same redirect, retirement, rotation and attacker-key certificate. This shrinks reach from the whole zone to Cloud-held names. It is a strict improvement but not containment. |
| **Separate authority**: move it, and bind every effect to customer-held authority | **Recommend** | Both halves are required. See below. |

### Separation proposal

This is a candidate for an implementation thread, not a selected design. It consumes thread A's trusted-key contract, which binds a key to allowed authority with a signed generation. It does not define new wire types.

**Administrative separation.** Hosted DNS, its env, the Route 53 IAM user, the ACME account and its DB run where np1 root has no shell, no deploy path and no database credentials. That means a different host, not in np1's Uncloud cluster, deployed from an operator machine. Its PlanetScale role and org cannot be reached with Cloud's credentials. Add `ployz.app CAA 0 issue "pki.goog; accounturi=<Hosted DNS account>"` so only the service's ACME account can issue. np1 can no longer change that record. Rotate everything in [Rotation](#rotation-and-revocation) at the move, since np1 has held all of it.

**Binding.** Hosted DNS pins, per name, the customer's authority root from A1's trusted key record. It accepts a later generation only when the previous pinned generation signed it. A new name is bound at reservation. The first generated-domain deploy is already an authorized workflow under C, so the Machine signs `bind {name, authority}` and Cloud relays it. A Cluster Domain survives teardown (`dashboard/CONTEXT.md:137`), so re-pairing needs a rebind signed by the pinned authority. A customer who lost all authority goes through a Ployz-staff rebind on the separated service. That residual is Ployz staff, not np1.

**Records from Machine claims.** Each ingress Machine signs a claim about itself only: `{name, machine_key, address, accepts_ingress, seq}`, with `machine_key` chained to the pinned authority. Hosted DNS builds the apex set from current claims. It probes `/.ployz-verify` itself and drops addresses that don't answer, which replaces Cloud's probe. A claim is withdrawn only by a signed withdrawal from that Machine or by the authority, for example inside an authorized Server removal or a web-traffic-off workflow. This fits **Machine-local authority**: a Machine speaks only for itself. Cloud relays claims, and the daemon still makes no Hosted DNS calls.

**Lease.** Expiry suspends a name and removes its records. It never retires one. Retirement needs an authority-signed request. A suspended name is restored by any valid signed claim.

**Certificates.** One Cluster-held key for `name` and `*.name`. The first ingress Machine generates it, and A1's recipient wrapping (the same path as the Sealing Key) shares it with trusted ingress Machines. A Machine signs `{name, spki_sha256, nonce}`, and Hosted DNS issues only when the CSR's key hash matches and the nonce is fresh. Cloud never holds the key. `publishClusterDomainCertificate` and `encrypted_certificate_private_key` go away.

**Rotate and mint.** `rotate` requires an authority signature, or the bearer token is dropped entirely in favour of signatures. Mint without a binding leaves a name that can't publish records, so the mint key can go.

#### Requests the separated service rejects, with np1 holding every Cloud credential

These assume np1 has every Cloud credential, a decrypted per-name token, every signed envelope Cloud ever relayed, and Cloud DB write access, which it can use to insert fake Machine and key rows.

```http
# 1. Arbitrary address: bearer token, no claim
PUT /domains/acme-x7q2.ployz.app/records
Authorization: Bearer <valid per-name token>
{"a":["203.0.113.66"]}
→ 401 {"error":"claim_signature_required"}

# 1b. Claim signed by a "Machine" key np1 inserted into Cloud's DB
POST /domains/acme-x7q2.ployz.app/claims
{"machine_key":"<np1-made key>","address":"203.0.113.66","seq":1,"chain":[<np1-made cert>],"sig":"…"}
→ 403 {"error":"untrusted_signer"}  chain does not reach the pinned authority generation

# 1c. Replay of a real Machine's earlier claim, after it moved to a new IP
POST /domains/acme-x7q2.ployz.app/claims   <captured claim, seq 41; stored seq 57>
→ 409 {"error":"stale_sequence"}

# 2. Unauthorized retirement
DELETE /domains/acme-x7q2.ployz.app
Authorization: Bearer <valid per-name token>
→ 401 {"error":"authority_signature_required"}
#    Withholding every renewal for 7+ days → name suspended, records removed (outage), not retired.
#    The next valid Machine claim restores it.

# 2b. Token rotation to lock Cloud out
POST /domains/acme-x7q2.ployz.app/rotate
Authorization: Bearer <valid per-name token>
→ 401 {"error":"authority_signature_required"}

# 3. Arbitrary CSR key, with a valid captured envelope
POST /domains/acme-x7q2.ployz.app/certificate
{"csr":"<CSR for acme-x7q2.ployz.app, *.acme-x7q2.ployz.app, attacker SPKI>",
 "authorization":{"spki_sha256":"<Machine key hash>","nonce":"n-91","sig":"<valid Machine sig>"}}
→ 422 {"error":"csr_key_mismatch"}
#    Same envelope with the Machine's own CSR replayed → 409 nonce_used
#    (and a cert for a key np1 doesn't hold is useless to it).

# 3b. Going around the service: np1 asks Let's Encrypt for *.acme-x7q2.ployz.app
→ np1 can't publish _acme-challenge (no Route 53 credentials), and CAA
  accounturi refuses any account but Hosted DNS's.
```

#### What np1 can still do after separation

np1 can withhold relays, so records go stale and names suspend after 7 days. That is an outage, which the promise allows. It can read names and addresses, which are public anyway. It can see signed envelopes, which are useless outside their binding. It can mint unbound names. It can lie in Cloud's domain status UI. Through `PublishCertificateMaterial` it can still override certificates on Machines until the server track gates that RPC.

| Concern | Proposed behavior | Status |
| --- | --- | --- |
| Initial ownership of existing names | One-time bind window at cutover: bearer token plus authority signature, accepted only while the name is unbound. If np1 is compromised during that window it can bind first. Each Machine reads `GET /domains/{n}/binding` (public), and the UI shows the pinned fingerprint. A mismatch is an operator incident. | Design. Residual is a TOFU race. |
| Address changes | Signed per-Machine claims, health-probed by Hosted DNS | Design |
| Routine renewal | Hourly relayed claims or renewals. A Machine signs from standing local authority, the "daemon-owned infrastructure maintenance stays local and narrow" case in `decisions.md`. No customer taps. Certificate renewal is Machine-initiated at 30 days left. | Design |
| Recovery | Authority rotation chains through A1 generations. Total loss means a Ployz-staff rebind. | Design, depends on A1 |
| Service failure | Route 53 keeps the last records, and Machines keep the current cert, with 30 or more days of headroom. Hosted DNS down for longer than the remaining validity breaks TLS. Same as today. | Design |
| Number of names and GTS rate limits | Not measured | U |

### Smaller steps worth taking regardless

- **`rotate` needs more than the bearer.** Cloud never calls it, so requiring an authority signature for it costs Cloud nothing. Only after separation does that requirement protect anything.
- **Cloud records an alert when Hosted DNS returns 401 on a valid row.** It already logs an error (`sync.server.ts:75`). Treat it as a possible token-rotation hijack, not only an incident.
- **CAA on `ployz.app`.** Cheap, but meaningless while np1 holds the Route 53 key that can rewrite CAA.

## Hand-offs

These are outside thread X's boundary. Send them through the operator.

- **A2, C or F (server track):** `PublishCertificateMaterial` accepts any hostname and any untrusted chain from an `Operator` caller, and published material outranks the Machine's own ACME (`corrosion/store.rs:918`). np1 can override certificates for customer custom domains, or `Clear` them. Either gate it under workflow authorization, or retire it once Machines hold the Cluster Domain key. This belongs in F's automatic-maintenance inventory: certificate delivery is listed in `decisions.md` as an existing automatic effect.
- **A1:** The separation proposal needs a customer authority root that outlives a Cluster, because a Cluster Domain survives teardown. It also needs recipient-wrapped sharing of a non-Sealing key between ingress Machines.
- **Terms (`core/CONTEXT.md` Hosted DNS and Certificate Material; `dashboard/CONTEXT.md:137` Cluster Domain):** These change if the proposal is selected. The runtime would hold its Cluster Domain name and key, and Cloud would stop holding the key.
- **Ops (Nick):** Hosted DNS's placement on np1 is the main finding. Moving it is an ops-repo change and a deploy, not code in this repo.

## DESIGN bets touched by the proposal

- **Cloud drives, never owns.** Cloud keeps relaying, but stops owning record choice, retirement and TLS keys.
- **Machine-local authority.** Each Machine signs claims about itself only. No Machine decides another's records. Hosted DNS takes the union.
- **Observer-relative truth.** The apex set is current signed claims plus Hosted DNS's own probe, reported as Hosted DNS's observation.
- **Evidence over claims.** The UI shows the pinned binding fingerprint, and shows nothing as protected without it.
- **Lean on proven primitives.** Ed25519 or ECDSA signatures, CAA accounturi, and standard ACME.
- **Stable promise.** New Hosted DNS endpoints and an end to Cloud-held keys. This needs the 0.4 cutover argument that F owns, with no permanent dual path.
