# Residual Review Findings

Source context: capability backend/runtime architecture slice on branch `feat/idiomatic-crate-boundaries`, reviewed with correctness, maintainability, and testing subagents.

- P1 `crates/ployz-nats/src/coord/rpc.rs`: Internal NATS node RPC still depends on public daemon response types. `NatsNodeRpcClient::request` still uses `DaemonRequest`/`DaemonResponse` through the NATS bridge, so public CLI/API response shape can still leak into peer RPC. Follow-up should finish the `ployz-node-api` split by making NATS speak only internal node command/response types and adapting to daemon responses at the `ployzd` edge.
- P2 `crates/ployz-cert-api/src/lib.rs`: The generic certificate API still owns ACME-specific contracts. This slice adds an issuer-neutral `CertificateIssuer` surface, but ACME account/order/challenge traits remain in the generic crate. Follow-up should move ACME-only coordination contracts into `ployz-cert-acme` or a narrow ACME contract crate.
- P2 `crates/ployzd/src/daemon/handlers/deploy.rs`: The deploy handler remains too large and still composes backend infrastructure with workflow policy. This slice moves node deploy runtime composition to capability backends, but deploy still owns NATS lock/client setup, certificate/deploy coordination, orchestration calls, and response shaping. Follow-up should extract a deploy operation service so the handler only maps request resources and responses.
- P2 `crates/ployz-node-runtime/src/lib.rs`: Node runtime is still foundational rather than the owner of daemon component lifetimes. This slice introduces runtime and supervision primitives, but `ployzd` does not yet route gateway, DNS, NATS, cert renewal, image receiver, ZFS transfer listener, or bootstrap peer seed through it. Follow-up should migrate one real long-lived component first, then continue by component class.
- P2 `crates/ployz-volume-docker/src/lib.rs` and `crates/ployz-volume-btrfs/src/lib.rs`: Non-ZFS backends need stricter constraint semantics before product-grade use. Docker volumes intentionally do not apply quotas, ownership, mode, or custom mountpoints; Btrfs still lacks quota enforcement. Follow-up should either reject unsupported constraints visibly per backend or add backend-specific capability fields that prove the requested intent was applied.
- P2 `crates/ployzd/src/daemon/handlers/control_dispatch.rs`: The control/node dispatcher split lacks direct tests for the public dispatch entry points. Lane classification is covered, but follow-up should assert `handle_command_shared`, `handle_command_exclusive`, `handle_node_shared`, and `handle_node_exclusive` reject wrong-lane or wrong-protocol requests directly.
