# Residual Review Findings

Source context: ZFS volume move execution slice on branch `codex/zfs-volume-move-execution`, reviewed with correctness, reliability, API-contract, maintainability, and testing subagents.

- P1 `crates/ployz-orchestrator/src/deploy/execute.rs`: Volume move failure can leave writers removed. This slice drains and removes writer instances before starting the ZFS move so the snapshot has a quiesced source. If the move then fails before commit, the deploy fails but does not yet restart or re-adopt the prior writer release. Follow-up should make writer quiescing reversible, or add a rollback path that restarts the prior release when the move fails before commit.
- P2 `crates/ployzd/src/daemon/handlers/deploy.rs`: Lock-loss abort can orphan an in-flight ZFS transfer. If deploy lock renewal fails before commit after `volume_zfs_send` has started a background transfer, the coordinator future is dropped and there is no transfer cancel/interrupt RPC tied to the deploy failure. Follow-up should track started transfer ids and issue explicit cancel/interrupt on lock loss or move timeout.
- P2 `crates/ployzd/src/daemon/handlers/deploy.rs`: Lock-loss post-commit branch is helper-tested but not full handler-flow tested. This slice verifies the state transition helper and avoids marking committed deploys failed, but a fuller harness should inject lock renewal timing into `handle_deploy_apply` and assert the apply result is returned after the commit point.
- P2 `crates/ployzd/src/daemon/handlers/volume/zfs.rs`: Stale ZFS move claim recovery is tested at `TransferStore` level, not through the daemon handler. Follow-up should add handler-level tests that seed a stale claim pointing to a failed or missing transfer and assert `handle_volume_zfs_send` replaces it.
